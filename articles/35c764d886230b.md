## はじめに

以下の記事にて、`Model::shouldBeStrict()`を使うことでEloquentの3つの挙動を厳格にする設定に触れました。

https://zenn.dev/naopusyu/articles/371afde869697b

1. N + 1 の検出
1. fillable / guarded の設定漏れによる属性破棄の検出
1. 存在しないプロパティへのアクセスの検出

また、記事では本番環境では設定を無効化する方法にも触れています。

```php
// 本番環境以外で有効
Model::shouldBeStrict(! app()->isProduction());
```

こうすることで本番環境では検知しても例外が起きないようになりますが、
実際は本番環境で検知したい！というケースは多いはずです。

ただ、ユーザーには影響を出したくないので、今回は例外を発生させないで方法について触れていきます。

## 環境

- PHP 8.5.8
- Laravel 13.22.0

## 例外の発生箇所を確認

まずはどこで例外を出しているのか確認です。
前の記事でも触れていますが、専用の例外クラスがあるのでそのクラス名で探せば良いです。

- N + 1 の検出の例外（`LazyLoadingViolationException`）

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Concerns/HasAttributes.php#L614-L625

- fillable / guarded の設定漏れによる属性破棄の検出の例外（`MassAssignmentException`）

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Model.php#L675-L715

- 存在しないプロパティへのアクセスの検出の例外（`MissingAttributeException`）

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Concerns/HasAttributes.php#L518-L531

## 例外を発生させない方法を確認

例外の発生箇所の処理をよく眺めるとコールバック関数が設定されていたら呼び出す処理があります。

※ 例：N + 1の検出の場合

```php
// コールバック関数が登録されていると例外の代わりにコールバック関数を実行する。
if (isset(static::$lazyLoadingViolationCallback)) {
    return call_user_func(static::$lazyLoadingViolationCallback, $this, $key);
}
```

つまり、コールバック関数を登録しておけば例外の発生を抑制し、環境を気にせず`Model::shouldBeStrict()`を使うことができそうです。

## コールバック関数を登録する方法を確認

まずはコールバック関数をどこで登録するのか確認です。
それぞれのコールバック関数を設定する変数名で探せば良いです。

- N + 1 の検出

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Model.php#L597-L600

- fillable / guarded の設定漏れによる属性破棄の検出

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Model.php#L619-L622

- 存在しないプロパティへのアクセスの検出

https://github.com/laravel/framework/blob/v13.22.0/src/Illuminate/Database/Eloquent/Model.php#L641-L644

専用のメソッドが用意されていることがわかりました。
このメソッドたちを使えば例外を抑制し、別の処理を動かすことができそうです。

:::message
実はN + 1についてはマニュアルに書いてあります。
https://laravel.com/docs/13.x/eloquent-relationships#preventing-lazy-loading
:::

## 実践

さきほど調べた各メソッドを使ってコールバック関数を登録し、実際に例外が起きないか確認します。

```php
use Illuminate\Database\Eloquent\Model;
use Illuminate\Support\Facades\Log;

Model::handleLazyLoadingViolationUsing(function ($model, $relation) {
    Log::warning('N+1 detected', [
        'model' => get_class($model),
        'relation' => $relation,
    ]);
});

Model::handleDiscardedAttributeViolationUsing(function ($model, $keys) {
    Log::warning('Mass assignment discarded', [
        'model' => get_class($model),
        'keys' => $keys,
    ]);
});

Model::handleMissingAttributeViolationUsing(function ($model, $key) {
    Log::warning('Missing attribute accessed', [
        'model' => get_class($model),
        'key' => $key,
    ]);
});
```

これらを`Model::shouldBeStrict()`と一緒に`AppServiceProvider`の`boot()`メソッドで設定しましょう。

前の記事でも使った確認用のコードを使って、例外が起きないことを確認します。

```php:routes/console.php
<?php

use App\Models\Task;
use App\Models\User;
use Illuminate\Support\Facades\Artisan;
use Illuminate\Support\Str;

Artisan::command('strict', function () {
    // N + 1の検出
    $user_ids = [];
    $tasks = Task::all();
    foreach ($tasks as $task) {
        $user_ids[] = $task->user->id;
    }

    // fillable / guarded の設定漏れによる属性破棄の検出
    Task::query()->create([
        'user_id' => 1,
        'title' => 'title',
    ]);

    // 存在しないプロパティへのアクセスの検出
    $user = User::first();
    echo $user->abc;
});
```

## まとめ

今回書いた内容を使えば例外を出さないでログに出力することで、本番環境でもユーザーには影響を出さないで問題がある箇所を特定することができそうです。

また、Slackに通知など、ログファイルに出力以外の方法も可能になります。
